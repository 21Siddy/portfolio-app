NSGA-II Topology-Aware RAG Selection

Investigating why standard vector search clusters around repetitive introductory paragraphs on multi-part queries, and how multi-objective graph optimization over document topology provides an encouraging initial signal.

Multi-Objective Genetic Algorithm (NSGA-II) Attributed Chunk Graph Graph Commute Distance Qwen 3.5 9B Benchmark Interactive 3D Explorer

01 The Problem with Vector Search

When you ask a complex question (like asking for a definition, a mathematical condition, and a real-world example in one prompt), standard vector search often fails. It ranks chunks purely by cosine similarity to the question. Technical documents usually repeat their main keywords across the title, abstract, and introductory paragraphs. As a result, the top 3 results are often three different ways of saying the exact same introductory point. The LLM gets a context window stuffed with repetitive definitions while missing the actual math and use-case sections located further down the document.

02 Framing Retrieval as a Trade-Off

To solve this clumping problem, I modeled the document as a graph where paragraphs are nodes connected by reading order and topic similarity. I then framed context chunk selection as a three-objective optimization problem:

For any candidate triplet of chunks $S = \{c_1, c_2, c_3\}$:

Objective 1 (Relevance): Chunks must still match the user question
$$f_1(S) = R(S) = \frac{1}{K} \sum_{i \in S} \cos(q, e_i)$$
Objective 2 (Redundancy): Chunks should not say the same thing to each other
$$f_2(S) = \operatorname{Red}(S) = \frac{2}{K(K-1)} \sum_{i < j \in S} \cos(e_i, e_j)$$
Objective 3 (Graph Spread): Chunks should be spread out across the document graph
$$f_3(S) = G(S) = \frac{2}{K(K-1)} \sum_{i < j \in S} \widehat{C}_{ij}$$
Constraint: Relevance Floor
$$g_1(S) = \tau - \min_{i \in S} \cos(q, e_i) \le 0 \quad (\tau = 0.35)$$

$f_3$ uses random-walk commute time distance $\widehat{C}_{ij}$ derived from the graph Laplacian. Maximizing graph spread forces the retriever to hop across conceptual boundaries (introductory concepts, mathematical proofs, and practical engineering examples) rather than staying inside a single paragraph cluster.

04 LLM Generation Comparison: Clustered vs. Topology-Aware

To evaluate whether the 3D knee point helps an LLM produce a better answer in practice, I tested both retrieval sets with a local qwen3.5-9b model (temperature 0.0, max 1200 tokens) using the retrieved contexts. Answers were then evaluated by an automated LLM judge across a 6-dimension rubric (30 points maximum).

Limitations & Open Questions

This project serves as a single-document proof-of-concept. Several practical challenges remain:

  • Scaling to Large Corpora: Running graph Laplacians on the fly works for small documents, but scaling to thousands of documents requires precomputing graph structures or using approximate random-walk diffusion.
  • Query Variety: Testing against multiple query types remains an open topic. Some simple factual queries may actually prefer local clustering rather than broad topological dispersion.
  • Parameter Decisions: Finding the best values for the relevance floor ($\tau = 0.35$) and edge weights remains an empirical tuning decision.
